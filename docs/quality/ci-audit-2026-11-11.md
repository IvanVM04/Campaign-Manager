## 1. Executive findings

The project already has useful CI coverage. The latest inspected run on `main` completed successfully for every job. However, the active repository ruleset has an empty `required_status_checks` list. Pull requests and review-thread resolution are enforced, but CI results are not currently configured as required merge checks.

This is the highest-priority CI gap. A green Actions page is not equivalent to a ruleset that blocks merges when checks fail.

The GitHub connector could read the active ruleset but could not read branch-protection settings or mutate the ruleset. A repository administrator must configure required checks in GitHub repository settings. Until that is done, the project's one-PR-at-a-time workflow must manually enforce the gate and must not merge a PR with pending, cancelled or failed checks.

## 4. Merge enforcement gap

The active repository ruleset `protc1` targets the default branch. It requires pull requests, requires review-thread resolution, and blocks branch deletion and non-fast-forward updates. Its required status-check configuration is currently:

```json
{
  "strict_required_status_checks_policy": true,
  "required_status_checks": []
}
```

A repository administrator should configure the stable check names reported by GitHub Actions after confirming the names for a fresh PR. At minimum require:
- `test`
- `lint`
- `Pyright (models, rules_engine, bootstrap, operations)`
- `test-js`
- `CI summary`
- the CodeQL language checks (or a stable CodeQL aggregate check)

Repository-wide Pyright now has zero errors and is promoted to a blocking CI gate. The JSON report remains an artifact for diagnosis; warnings and information are reported but do not block. The job also fails on installation, invocation, malformed-report or other infrastructure errors. Coverage remains report-only until an incremental policy is designed.

**Do not confuse workflow-blocking with merge-blocking.** The jobs fail their workflow when a blocking step fails; the empty ruleset list means GitHub is not currently using their statuses as mandatory merge conditions.

## 5. CI weaknesses and opportunities

### 5.1 Dependency reproducibility

The test workflow installs `pytest`, `pytest-cov` and `httpx2` without exact pins. Ruff is installed without a version pin. The Pyright package is pinned, but the required Pyright job uses older major versions of `actions/checkout` and `actions/setup-python` than the other jobs. Application runtime dependencies in `requirements.txt` are also unpinned.

The PEP 735 dependency groups in `pyproject.toml` now separate test, lint and typing tools with exact direct pins. PR #171 makes CI install those groups rather than maintaining a second set of package declarations in workflow YAML. Runtime dependencies remain in `requirements.txt` and are deliberately outside this tooling-only change.

**Status after PR #171 and #172:** direct test/lint/type-check tool versions are centrally pinned and used by local setup and CI. All checkout/setup actions in the test workflow now use the same major version. Transitive dependencies are still resolved by pip and are not fully locked. A future lockfile decision should weigh the additional maintenance against the project's current deployment model. Runtime dependency upgrades remain separate from CI maintenance.

### 5.2 Quality baseline reliability

The repository-wide Pyright job now fails when the JSON report contains any error diagnostic, while retaining the report artifact and allowing warnings/information to remain visible without blocking. Tool/configuration failures also fail the job. It is included in the aggregate CI summary.

### 5.3 Coverage

Coverage is collected for both lines and branches, uploaded as an artifact, and summarized by top-level package in the GitHub Actions job summary. The latest inspected report (PR #172, application code unchanged from `main`) measured 85.95% line coverage and 72.74% branch coverage.

| Package | Line coverage | Branch coverage |
|---|---:|---:|
| `api` | 80.3% | 83.3% |
| `services` | 84.4% | 73.7% |
| `repositories` | 86.4% | 70.4% |
| root-level modules | 87.3% | 91.4% |
| `models` | 88.1% | 65.0% |
| `rules_engine` | 89.4% | 73.5% |
| `bootstrap` | 100% | 100% |
| `operations` | 100% | n/a |

The package percentages are descriptive, not quality scores: package size and risk differ, and 100% in small packages should not be treated as equivalent to broad critical-path protection. The package summary reports branch totals where Cobertura exposes them; the aggregate branch rate remains 72.74%. The low branch rates in `models` (65.0%), `repositories` (70.4%) and `services` (73.7%) are useful candidates for risk-based test review.

Do not set an arbitrary global gate. Use the package report to identify uncovered critical branches (transaction rollback, stale revisions, lease expiry, invalid model output, forbidden operations, retry idempotency), then introduce an incremental no-regression policy.

### 5.4 Security and dependency automation

CodeQL and Dependabot are now present. Review alerts and dependency PRs rather than adding more overlapping scanners immediately. SonarQube is optional and should be evaluated only after identifying a signal not already covered by Ruff, Pyright, tests, coverage or CodeQL.

### 5.5 Workflow efficiency and feedback

The test workflow cancels superseded runs for the same pull request or branch, while keeping different pull requests independent. Its `CI summary` job always publishes the result of every check and fails if any required job did not succeed. CodeQL remains a separate workflow with its own status checks and security summary.

### 5.6 Platform and integration coverage

The current deterministic workflow runs on Ubuntu with Python 3.12 and the JavaScript suite on Node 20. This is a clear supported CI baseline, not cross-platform certification. Keep live Ollama/SillyTavern checks separate, explicit and reproducible.

## 7. Acceptance policy

Until GitHub's ruleset is configured, manually inspect the PR's complete check list. No PR is ready to merge while an applicable check is failing, pending or cancelled. Fix failures on the same branch. A successful deterministic run does not certify Ollama availability or a real SillyTavern session.
