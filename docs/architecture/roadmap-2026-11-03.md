# Architecture consolidation roadmap

**Date:** 2026-11-03  
**Baseline:** `main` at `5fbcb86f357350de9b77f386344d7babf6f681c0`

This roadmap turns the architecture audit into incremental work. It is intentionally ordered by risk reduction, not by how visible a feature would be.

## Guiding rules

- Keep the modular monolith and SQLite.
- No mass package moves.
- No new game mechanics while a prerequisite architectural invariant is unclear.
- Every change is a focused PR with tests and a rollback/compatibility plan.
- Preserve API paths, campaign scoping and SillyTavern turn identifiers unless a migration is explicitly designed.
- A finding can be deferred only with a documented reason and owner/trigger.

## Phase 0 — Complete the audit baseline (this PR)

**Deliverables:** current architecture map, ownership boundaries, engineering findings, ADRs and this roadmap.

**Exit criteria:**
- The two turn paths are documented separately.
- State ownership and cross-aggregate invariants are explicit.
- Static review limits are stated honestly.
- No production code changes are included.

## Phase 1 — Stabilize API composition and contracts

**Suggested next PR: #20**

1. Extract FastAPI routers by capability while preserving endpoint paths and request/response schemas.
2. Create one explicit application composition root; remove obsolete factory/proxy scaffolding only after all call sites/tests are migrated.
3. Define stable application error categories and a central HTTP mapping.
4. Add API contract tests for status codes, campaign scoping and error payload shape.

**Do not:** move domain services or change turn behaviour in the same PR.

**Exit criteria:** route modules are transport-only; app construction is clear; endpoint contracts remain backward compatible.

## Phase 2 — Make transaction ownership explicit

**Suggested PR: #21**

1. Introduce a narrow SQLite Unit of Work / transaction runner.
2. Migrate one high-value use case first (native turn commit or combat attack), not all services at once.
3. Ensure repositories participate in caller-owned transactions.
4. Add failure-injection tests proving no partial writes and no stale in-memory state after rollback.
5. Document lock ordering and the single-process constraint.

**Exit criteria:** transaction boundaries are visible at application-use-case level and covered by rollback tests.

## Phase 3 — Unify turn consequence contracts

**Suggested PRs: #22–#24**

1. Define typed intent/adjudication/consequence models and explicit authority policy.
2. Separate structured consequence planning from final narrative generation.
3. Validate actor, target, ownership, campaign scope, preconditions and idempotency before mutation.
4. Persist a durable resolution record before final narration.
5. Make narration retryable without reapplying state changes.
6. Adapt SillyTavern as an adapter to the same consequence application contract; preserve external turn version/snapshot reconciliation.
7. Add integration tests for stale plans, provider failure, commit failure, narration failure/retry and malicious/invalid model proposals.

**Exit criteria:** a turn can be resolved exactly once, persisted, and narrated/re-narrated without duplicating consequences; both entry paths enforce the same state authority.

## Phase 4 — Clarify mechanical state ownership

**Suggested PRs: #25–#26**

1. Formalize the canonical character mechanical aggregate.
2. Document encounter combatant snapshots as projections and centralize PC HP synchronization.
3. Decide NPC persistence and condition ownership before extending either.
4. Define a unified lifecycle for persistent, temporary, campaign-time and round/turn effects.
5. Decide inventory/equipment ownership and derived attack-profile rules.

**Exit criteria:** no new feature can write the same mechanical fact through competing services.

## Phase 5 — Establish domain package boundaries

**Suggested PRs: #27 onward**

Migrate incrementally into feature-oriented modules only after dependencies are mapped:

- campaign/session;
- world/memory;
- character;
- inventory/equipment;
- combat/encounter;
- effects/conditions;
- clock/time;
- turns/AI orchestration;
- rulesets;
- integrations.

Use compatibility imports during each move. Enforce dependency direction with lightweight import tests or lint rules.

**Exit criteria:** domain dependencies are explicit and accidental cross-domain imports are detectable.

## Phase 6 — Provider/runtime lifecycle and operations

1. Centralize validated provider URL/model/timeout and model-role settings.
2. Add runtime cache lifecycle/invalidation on campaign deletion/configuration changes.
3. Define graceful startup/shutdown for provider/runtime resources.
4. Keep single worker until cache/world-state coherence has an explicit design.
5. Add token-aware context budgeting when model/provider selection is configurable.

**Exit criteria:** runtime configuration is testable and no hidden global provider assumptions remain.

## Phase 7 — Product experience

Only after the core loop is reliable:

1. standalone web UI;
2. complete character sheet and character creation/progression;
3. exploration and social interaction workflows;
4. broader combat, spells and class features;
5. VTT as a separate, distant phase.

## Recommended immediate next step

After PR #19 is reviewed and merged, start **PR #20: API composition extraction and error-contract consolidation**.

It is a bounded change that improves the structure we will need for every later phase, without changing game rules or turn semantics. Keep the turn-pipeline redesign out of PR #20; it deserves its own design and tests.
