# Architecture consolidation roadmap

**Date:** 2026-11-04  
**Baseline:** `main` at `c5cc24d9988ae03e3dca3d4c0a62cb52742ad780`

This roadmap orders work by risk reduction and architectural dependency, not by visible feature count.

## Guiding rules

- Keep the local-first modular monolith and SQLite.
- No mass package moves or generic workflow framework.
- No new game mechanics while a prerequisite architectural invariant is unclear.
- Every change is a focused PR with tests and a compatibility/recovery plan.
- Preserve API paths, campaign scoping, and SillyTavern turn identifiers unless an explicit migration is designed.
- Inspect existing models, repositories, migrations, and adapters before adding parallel concepts.
- Keep the single-process deployment constraint until runtime cache and locking semantics are redesigned.

## Phase 1 — Durable turn-resolution lifecycle

The target architecture is specified in [ADR-012](architecture-decisions-2026-11-03.md) and [the lifecycle contract](turn-resolution-lifecycle.md).

1. **PR #28 — Contract (merged):** define lifecycle states, request identity/idempotency, trust boundaries, atomic consequence commit, narration isolation, and crash recovery.
2. **PR #29 — Persistence (this PR):** migration 022 and a linked durable resolution envelope; keep the existing `turns` table as historical transcript; enforce identity, legal transitions, context evidence, and planning leases.
3. **PR #30 — Native pipeline (next):** create durable resolution records from native requests; persist prepared plans; atomically commit consequences and resolution state; generate narration after commit and retry it independently.
4. **PR #31 — SillyTavern adapter:** route external turns through the same application contract while preserving external turn IDs, versions, snapshots, and regeneration behaviour.
5. Follow-up: durable manual-roll and clarification continuation; recovery orchestration; remove narrative-derived consequence extraction once structured proposals are fully adopted.

**Exit criteria:** a request can be recovered after process restart; domain consequences are committed at most once; stale plans cannot mutate state; narration can fail and retry without changing committed outcomes; native and external adapters share authorization and persistence guarantees.

## Phase 2 — Clarify mechanical state ownership

- Formalize canonical character mechanical state and encounter projections.
- Decide NPC persistence and condition ownership before extending either.
- Define one lifecycle for persistent, temporary, campaign-time, and round/turn effects.
- Continue inventory/equipment ownership and derived combat-profile rules.

**Exit criteria:** no mechanical fact can be written through competing authoritative services.

## Phase 3 — Complete the D&D 5e 2014 core loop

Prioritize prerequisites and vertical slices: character creation/progression; equipment-derived AC and defenses; combat action economy/movement/range; HP/death saves/concentration; spells and class resources; rests and effect expiry.

Each feature must use deterministic rules code, canonical state ownership, typed operations, and integration tests. D&D 2024 remains a separate ruleset phase.

## Phase 4 — Domain boundaries and runtime lifecycle

- Strengthen feature-oriented package boundaries incrementally, using compatibility imports.
- Centralize validated provider URL/model/timeout and model-role settings.
- Add runtime cache lifecycle/invalidation and graceful startup/shutdown.
- Add token-aware context budgeting.
- Keep one worker until cache/world-state coherence is explicitly addressed.

## Phase 5 — Product experience

Only after the core campaign loop is reliable:

1. standalone web UI;
2. complete character sheet and creation/progression;
3. exploration and social workflows;
4. broader combat, spells, and class features;
5. VTT as a separate, distant phase.

## Current next step

PR #29 adds the durable persistence primitives but does not yet connect them to turn execution. After it is reviewed and merged, PR #30 should wire the native pipeline to these records and prove atomic consequence commit plus narration recovery. Do not claim exactly-once behaviour until those application boundaries are implemented and tested.
